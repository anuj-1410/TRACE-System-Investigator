Complete Project Details

============================================================
2. PROJECT DOMAIN
============================================================

Deep Learning + Cybersecurity + Digital Forensics + Probabilistic Reasoning


============================================================
3. BRIEF PROJECT DESCRIPTION
============================================================

AI-Based Cyber Incident Investigation is a system that analyzes system and
network logs to detect suspicious activities and understand what happened
during a cyber incident.

The system will not only detect abnormal behavior, but will also reconstruct
the sequence of events, identify the probable root cause, explain the evidence,
estimate the impact, and perform “what-if” simulations to understand whether
an earlier response could have reduced the incident.

The main idea is:

Detect -> Reconstruct -> Explain -> Simulate -> Respond


============================================================
4. PROBLEM STATEMENT
============================================================

When a cyber incident occurs, a very large number of system and network logs
may be generated. Manually analyzing these logs to determine what happened,
how the incident progressed, and what caused it can be difficult and
time-consuming.

This project aims to automate this investigation process using deep learning
and probabilistic reasoning techniques.


============================================================
5. PROBLEM THIS PROJECT SOLVES
============================================================

The project solves the problem of manually analyzing large amounts of system
and network logs after a cyber incident.

It automatically detects suspicious activity, reconstructs what happened,
identifies the probable root cause, and provides evidence-based insights to
help investigators understand and respond to the incident.


============================================================
6. MAIN IDEA
============================================================

Suppose the system logs contain the following sequence:

Unusual Login
    ->
Privilege Change
    ->
Suspicious Process
    ->
External Connection
    ->
Large Data Transfer
    ->
File Deletion

A normal intrusion detection system may only say:

"Suspicious activity detected."

Our system will go further and attempt to answer:

1. Did something abnormal happen?
2. What type of incident may have occurred?
3. What happened first and what happened next?
4. What is the probable root cause?
5. What evidence supports that conclusion?
6. Which users, systems, or resources may have been affected?
7. What may have happened if a defensive action had been taken earlier?
8. What actions should be recommended to the investigator?

7. PROJECT OBJECTIVES
============================================================

The main objectives are:

1. Analyze system and network event logs.
2. Detect abnormal or suspicious behavior.
3. Identify the likely type of cyber incident.
4. Discover hidden behavioral patterns in the logs.
5. Reconstruct the sequence or timeline of an incident.
6. Determine the probable root cause using evidence.
7. Estimate affected users, systems, and resources.
8. Perform counterfactual or “what-if” analysis.
9. Generate a final incident investigation report.
10. Demonstrate practical use of Deep Learning-II concepts such as:

11. MODULE 1 – LOG / EVENT PREPROCESSING
============================================================

Purpose:
Convert raw system and network logs into a common structured format that can
be processed by machine learning and deep learning models.

Example fields:

- Timestamp
- User
- System / Device
- Event Type
- Source
- Destination
- Process
- File / Resource
- Network Connection
- Severity
- Status

Example:

Timestamp | User  | System | Event             | Severity
10:01     | user1 | PC01   | Login             | Low
10:04     | user1 | PC01   | Privilege Change  | High
10:06     | user1 | PC01   | Process Start     | Medium
10:08     | user1 | PC01   | External Connect  | High

Tasks in preprocessing may include:

- Handling missing values
- Encoding categorical features
- Normalization/scaling
- Converting timestamps into useful features
- Building event sequences
- Removing duplicate/noisy entries
- Preparing model-ready feature vectors


============================================================
12. MODULE 2 – ANOMALY DETECTION USING VAE
============================================================

Full Form:
VAE – Variational Autoencoder

Purpose:
Detect unusual or abnormal system behavior.

The VAE will learn patterns representing normal behavior.

If a new sequence is very different from normal behavior, the reconstruction
error will be larger and the system can mark it as suspicious.

Simple idea:

Normal Behavior
    ->
Low Reconstruction Error
    ->
Normal

Abnormal Behavior
    ->
High Reconstruction Error
    ->
Possible Incident

Output example:

Anomaly Score: 0.91
Status: Suspicious Activity Detected


============================================================
13. MODULE 3 – HIDDEN PATTERN LEARNING USING RBM
============================================================

Full Form:
RBM – Restricted Boltzmann Machine

Purpose:
Learn hidden relationships and patterns among events.

For example, the following combination may represent a suspicious hidden
pattern:

Login
+
Privilege Change
+
New Process
+
External Connection

The RBM helps discover latent/hidden features that may not be obvious from
individual log entries.

RBM training can use:

- Contrastive Divergence
- Gibbs Sampling


============================================================
14. CONTRASTIVE DIVERGENCE
============================================================

Full Form:
CD – Contrastive Divergence

Purpose:
Used as a practical training method for the Restricted Boltzmann Machine.

It helps update the RBM weights so that the RBM learns useful probability
distributions and hidden representations from event data.


============================================================
15. GIBBS SAMPLING
============================================================

Purpose:
A probabilistic sampling technique used with RBMs and probabilistic models.

In this project, it may be used during RBM training/inference to sample hidden
and visible states.


============================================================
16. MODULE 4 – INCIDENT IDENTIFICATION
============================================================

Purpose:
Determine what type of incident is most likely occurring after suspicious
behavior is detected.

Instead of only returning:

Attack = Yes

the system may generate multiple hypotheses such as:

Account Compromise       72%
Privilege Escalation     81%
Data Exfiltration        87%

This allows the system to represent uncertainty rather than making an
absolute claim.


============================================================
17. MODULE 5 – TIMELINE RECONSTRUCTION USING MARKOV CHAIN
============================================================

Purpose:
Understand how the incident progressed through different stages.

Possible states:

Normal
  ->
Initial Access
  ->
Privilege Change
  ->
Suspicious Execution
  ->
External Communication
  ->
Data Transfer
  ->
Evidence Removal

The Markov Chain can estimate transition probabilities such as:

Normal -> Login              0.42
Login -> Privilege Change    0.31
Privilege -> Process         0.67
Process -> Network           0.73
Network -> Data Transfer     0.81

This allows the system to:

- Reconstruct incident progression
- Understand common event transitions
- Estimate what stage may follow the current stage
- Compare observed sequences with learned attack patterns


============================================================
18. MODULE 6 – ROOT CAUSE ANALYSIS USING BAYESIAN NETWORK
============================================================

Purpose:
Use available evidence to estimate the most probable cause of the incident.

Example relationship:

Unusual Login
    ->
Credential Compromise
    ->
Privilege Escalation
    ->
Suspicious Process
    ->
External Connection
    ->
Data Exfiltration

Observed evidence could include:

- Unusual login
- Privilege change
- Suspicious process
- Large data transfer

The Bayesian Network may produce:

Compromised Account     0.84
Insider Activity        0.11
Misconfiguration        0.05

This is probabilistic reasoning, so the result is a probable explanation,
not guaranteed truth.


============================================================
19. EVIDENCE-BASED EXPLANATION
============================================================

The system should show WHY it reached a conclusion.

Example:

Probable Cause:
Compromised Account

Supporting Evidence:
- Unusual authentication
- Privilege escalation
- Suspicious process execution
- External communication
- Abnormal data transfer

This makes the project more explainable and useful for investigation.


============================================================
20. MODULE 7 – IMPACT ANALYSIS
============================================================

Purpose:
Estimate what components may have been affected.

The system may report:

- Affected users
- Affected machines
- Suspicious processes
- External connections
- Potentially affected files/resources
- Possible data exposure
- Incident severity

Example:

Affected Systems: 2
Affected Users: 1
Suspicious Processes: 3
External Connections: 2
Potential Data Exposure: High
Incident Severity: High


============================================================
21. MODULE 8 – COUNTERFACTUAL / “WHAT-IF” ANALYSIS
============================================================

This is one of the advanced and important features.

Purpose:
Estimate how the incident might have changed if a response action had been
taken earlier.

Original Sequence:

Login
  ->
Privilege Escalation
  ->
Process Execution
  ->
External Connection
  ->
Data Transfer

What-if Question:

"What if the user account had been disabled immediately after privilege
escalation?"

The system may simulate an alternative progression and estimate that later
suspicious stages become less probable.

Example Output:

Intervention:
Disable account after privilege escalation

Estimated downstream suspicious events:
Before intervention: 4
After intervention: 1

Estimated Risk Reduction: 73%

Important:
This is only a probabilistic/model-based simulation. It does not guarantee
what would actually have happened in a real incident.


============================================================
22. MODULE 9 – SYNTHETIC INCIDENT GENERATION USING GAN
============================================================

Full Form:
GAN – Generative Adversarial Network

Status:
Optional / Bonus Feature

Purpose:
Generate additional synthetic incident sequences for testing and training.

Example real sequence:

Possible generated variations:

Login -> Privilege -> Process -> Network -> Transfer -> Delete

The generated samples can be used to test whether TRACE can detect and
investigate scenarios it did not directly see during training.

34. WHAT WILL NOT BE IMPLEMENTED
============================================================

To keep the project realistic and achievable, the following are outside the
initial scope:

1. A complete antivirus system
2. A full enterprise IDS/IPS
3. Automatic exploitation or penetration testing
4. Attacking real systems
5. Automatically deleting files or shutting down systems
6. Automatically blocking IP addresses in production
7. Supporting every possible cyberattack
8. Full enterprise-scale SIEM functionality
9. Guaranteed real-time operation in the first version
10. Guaranteed causal truth from limited evidence

The system will recommend actions and simulate scenarios rather than
automatically executing destructive or security-sensitive actions.


============================================================
35. PROJECT LIMITATIONS
============================================================

1. Accuracy depends on the quality of available logs.
2. Missing or incomplete evidence may reduce root-cause accuracy.
3. Model probabilities are estimates, not absolute facts.
4. The project will support a limited set of incident types.
5. Counterfactual results are simulations, not guaranteed outcomes.
6. Performance on completely different real-world environments may require
   retraining or adaptation.
7. The first version is primarily offline/batch-based rather than a full
   real-time production system.
